# Modo escaparate y control del log (2026-11-20)

Show mode for the car show, plus a switch that stops the app writing its log
file. Both features must leave a normal drive, with the OBD adapter connected,
exactly as it is today.

## What is asked

1. Something flashy for the car show: the app has to look alive on a stand,
   with no car and no adapter behind it.
2. Stop writing the log file to the Memory Stick.

## Constraints

- **The driving path is not touched.** Every new branch tests `g_cfg.show` or
  `g_cfg.log`. With `show=0` and `log=2` (today's values) the code takes the
  same path it takes now: same WiFi attempt, same ELM327 handshake, same
  scheduler, same drawing.
- **The demo data already exists and is reused, not rewritten.** `demo_toggle()`
  (hold L+R for 1.5 s) already synthesises a full driving cycle and stores it
  with `OBD_SRC_SIMULATED`. Show mode switches that same generator on at boot;
  it does not add a second source of fake values and does not change one number
  of what the demo produces.
- **Read-only toward the car.** In show mode nothing is sent: no WiFi, no
  adapter, no requests. No new OBD service is introduced anywhere.
- **Nothing is written to the Memory Stick during a show.** No log file, no
  settings rewrite.
- The Memory Stick holds no deletions, and the EBOOT on the card is replaced
  only after a review and a hash check.

## Design

### 1. Setting `show` (off by default)

- `settings.txt`: `show=0` (new key; `escaparate=` accepted as an alias).
- Settings menu: a row **MODO SHOW** (English: SHOW MODE) right after **LOG**,
  value ON/OFF with the existing `tr()` table.
- Persisted like every other setting; announced next to LOG in the table.

### 2. Boot with `show=1`

`main()`:

1. `settings_load()` runs before `log_open()` (the log switch has to be known
   before deciding whether to open a file at all).
2. If `show`: `demo_toggle()` before the dashboard so the first frame already
   has data; the network-module block is skipped entirely (no
   `sceUtilityLoadNetModule`, no "INICIANDO RED" banner).
3. `run_dashboard()` is entered with `sock = -1` and never calls
   `connect_network_and_elm()`, so no WiFi profile is touched and no adapter is
   waited for.
4. The opening screen is forced to GENERAL (the big dashboard) instead of the
   remembered screen.

Result: power on → MX-5 splash → live dashboard in about two seconds.

### 3. Rotation (the flashy part)

Inside `run_dashboard()`, only while `g_cfg.show`:

- Every 12 s the screen advances through the four driving screens
  (`mode_step()`, the same helper L/R uses): GENERAL → MOTOR → DIAG → TELEM.
- Every 30 s the theme advances through `0, 5, 6, 7, 8, 9, 10, 11, 12, 13`
  (the four colour variants of NORMAL are skipped, as the menu does), through
  `settings_apply()`, so the whole panel changes palette, including the game
  themes.
- Any button press pauses both rotations for 60 s, then they resume. Rotation
  is also paused while the settings menu or the screen picker is open.

### 4. The log switch

`log_full` (0/1) becomes `log` (0/1/2), because a middle state is what a real
drive wants:

| value | writes | use |
|---|---|---|
| 0 | no file at all | show, or a drive nobody needs to reconstruct |
| 1 | boot lines, the 2 s status line, one line per command with its timing, and the final summary | normal |
| 2 | also the parsed reply of every command (today's `log_full=1`) | debugging |

- Default is 2, so nothing changes for the card as it is.
- Migration: an existing `log_full=1` reads as `log=2`, `log_full=0` as
  `log=1`; the new file is written with `log=`.
- `log_open()` returns without creating a file when `log=0` **or** show mode is
  running. No file also means no `SIN LOG` warning in the top bar, because the
  switch was deliberate.
- Menu row LOG shows OFF / SESSION / FULL.
- `settings_load()` now runs before `log_open()`, because the LOG value decides
  whether a file is opened at all. The lines the loader used to write straight
  away (a truncated settings file, the telemetry-series migration, and the
  `Ajustes: tema=… contraste=… vista=…` summary that heads every log) are
  buffered and flushed by `settings_log_summary()` right after the banner, so
  no session loses them.

### 5. A show leaves nothing behind, and one session long

- The rotation changes `g_cfg.theme` so the panel really changes, but
  `settings_save()` writes `g_save_theme`, which only the user's own theme
  change updates. The show cannot rewrite the stored theme.
- The "save the current screen" writer in the 2 s status block is skipped in
  show mode.
- The only settings write of a show session is the one at a clean exit, and it
  exists to put `show=0` and the pre-show screen back on the card: the next
  power-on is a normal boot with its adapter. A session that ends by pulling
  the power keeps `show=1`, which is what a show wants between visitors.
- No log file is opened at all, so nothing else touches the card.

### 6. Surviving a stand

The PSP sits in a stand with people pressing buttons. In show mode `pressed` is
masked down to the D-pad and the triggers, so:

- L+R does nothing: nobody can switch the simulated data off and leave the
  dashboard saying N/D.
- START (menu) and SELECT (screen picker, telemetry series editor) do nothing:
  nobody can leave the app in a menu, in the series editor, or with the picker
  covering the screen. Without the menu there is also no row to press that could
  turn the mode off mid-show.
- TRIANGLE/SQUARE (reconnect, WiFi setup) and CROSS (probes and editors) do
  nothing: nobody can park the app on a WiFi or "SIN ADAPTADOR" screen.
- The D-pad and L/R still step through the four driving screens, which pauses
  the rotation for a minute; harmless, since it resumes.
- The owner exits with **SELECT+START held two seconds**, and START held no
  longer exits: a visitor leaning on START cannot end the demo.

## Files

`src/psp/main.c` only: settings struct, parse and save, menu draw and input,
`log_open()`, the boot block in `main()`, and the rotation inside
`run_dashboard()`. No changes under `src/core`, `include/`, or `tests/`.

## Risks and how they are covered

| risk | cover |
|---|---|
| The driving path changes without `show` | every new branch tests `show`/`log`; with the card's values the executed path is the current one |
| The settings file changes shape | `log=` written, `log_full=` still read; `version=2` unchanged |
| A save during the show rewrites the theme | `g_save_theme` is the only value written |
| Settings read a line before the log opens | `settings_load()` moved first; only settings-loader lines issued before `log_open()` are lost, and those are the malformed-file warnings |
| 22 menu rows no longer fit | two columns of 11 at 16 px pitch, the same panel height |
| The show gets a log file anyway | `log_open()` refuses when `show=1`, verified in the emulator by listing the data folder before and after |

## How it gets verified

1. `cargo`-less host build: `~/work/build.sh` (warnings as errors, host tests,
   EBOOT hash).
2. Emulator, `show=1`: boots with no adapter and no WiFi wait; screenshots at
   6/18/30/42/54/66 s show the screen and the palette changing; the data folder
   listing is identical before and after (no log file).
3. Emulator, `show=0 log=2`: the DEMO chord still works and the log is written
   exactly as today.
4. Emulator, `log=0`: no file appears and no `SIN LOG` marker is drawn.
5. A diagnostic build with the log forced on in show mode, read to confirm the
   rotation times textually (`Show: pantalla`/`Show: tema` lines), then the
   real build restored.
6. Review of the diff (GLM 5.3 high for the C, DeepSeek v4.1 flash high for the
   input and the settings semantics) before anything reaches the card.
7. Copy to the Memory Stick with the sha256 checked on the stick.

## Review outcome (2026-11-20)

Two reviewers read this plan and the diff: GLM 5.3 high on the C, DeepSeek
v4.1 flash high on the regression risk. Both said FIX-FIRST, and both were
right about the two things that mattered:

| found | fix |
|---|---|
| `show=1` was persisted and never cleared, so the next ordinary boot would drive on simulated data with no adapter (DeepSeek, blocker) | a clean exit writes `show=0`: the mode lasts one session |
| settings were written during a show (menu keypress, menu close, exit) while the plan promised no card writes (DeepSeek, blocker) | the menu and the picker are unreachable in show mode; the only write left is the exit that clears the mode |
| START held exited the demo, and the menu could turn show off (DeepSeek, blocker) | exit is now SELECT+START held two seconds; the menu and the picker are unreachable in show mode |
| the telemetry editor could open during the rotation, and every arrow in it saves the settings (GLM, should-fix) | CROSS is masked in show mode, so no editor opens |
| the settings summary line was dropped from every log by the `settings_load`/`log_open` reorder (both) | `settings_log_summary()`, flushed right after the banner |
| toggling SHOW in the menu started the rotation immediately with a live link (GLM) | show mode is a boot-time flag (`g_show_run`): the menu row applies to the next power-on |
| theme 11 `NOTHING` was in the rotation (both) | dropped from the ring |
| the log table called state 1 "session lines" when per-command lines were still written (DeepSeek) | table corrected above; the code keeps today's `log_full=0` volume |
| duplicated `COMPLETO` translation entry, `g_save_theme` with no single setter, `log`/`show` missing from the defaults block (GLM) | all three cleaned up |

Not fixed, on purpose:

- No host test covers the settings parser: `tests/Makefile` only compiles
  `src/core`, and moving the parser there the night before a demo is more risk
  than the test buys. Filed as follow-up work.
